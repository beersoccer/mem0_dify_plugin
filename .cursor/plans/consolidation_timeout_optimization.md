# 会话级记忆抽取工具超时优化方案

## 优化日期
2026-01-24

## 问题背景

### 使用场景
- **功能**: 定期(以天为单位)扫描指定用户在指定应用中的新会话消息,抽取长期记忆
- **触发频率**: 每天1次(通常在凌晨)
- **正常情况**: 一个应用只有一个长期记忆抽取工作流
- **异常情况**: 配置错误可能导致并发执行

### 原有超时设置的问题

| 维度 | 原设置 | 问题 |
|------|--------|------|
| `hard_time_budget_sec` | 55秒 | 对批量处理严重不足 |
| 锁 TTL | 3600秒(1小时) | 过长,任务崩溃后锁定时间过久 |
| Dify API timeout | 20秒 | 对大会话列表可能不足 |
| 设计目标 | 适配 `MAX_REQUEST_TIMEOUT=60s` | 实际是批处理,不应受此限制 |

**核心矛盾**: 
- 该工具是**批处理任务**(定期、非实时),不应受实时工具的60秒限制
- 单个用户可能有10+会话,每会话100+消息,每消息需3次Mem0写入(semantic/episodic/procedural)
- 估算: 10会话 × 5段 × 3类型 × 2秒 = **300秒** (5分钟)

## 优化方案

### 1. 时间预算 (hard_time_budget_sec)

**优化**: 55秒 → **300秒 (5分钟)**

**理由**:
- 对标 `add_memory` 工具的 30秒单次写入超时
- 批量巩固需要执行数十到数百次 Mem0 操作
- 定期批处理场景可以接受较长处理时间
- 用户不在等待,完整性 > 响应速度

**计算依据**:
```
典型场景:
- 10个会话/用户/天
- 每会话平均50条消息
- 按30条/段分段 ≈ 17个段
- 每段3种记忆类型(semantic/episodic/procedural)
- 每次 Mem0 add 平均耗时: 1-2秒(LLM推理+向量存储)

总耗时估算:
17段 × 3类型 × 2秒 = 102秒
加上 Dify API 调用(10+17次) × 1秒 = 27秒
合计: ~130秒

保守设置: 300秒(2.3倍冗余)
```

### 2. 分布式锁 TTL

**优化**: 3600秒(1小时) → **600秒 (10分钟)**

**理由**:
- TTL = 2 × 预期任务时长(提供安全边际)
- 10分钟对于每日批处理任务是可接受的恢复时间
- 大幅降低任务崩溃后的锁定影响
- 仍然足够覆盖异常慢的场景(大量历史数据)

**对比分析**:

| 场景 | 1小时TTL | 10分钟TTL |
|------|---------|----------|
| 正常完成(5分钟) | ✅ 正常释放 | ✅ 正常释放 |
| 任务崩溃 | ❌ 锁定1小时 | ✅ 10分钟自动恢复 |
| 超大历史(8分钟) | ✅ 能完成 | ✅ 能完成 |
| 异常慢(15分钟) | ✅ 能完成 | ⚠️ 可能超时但可重试 |

**风险评估**: 
- 极端慢的场景(>10分钟)可能被锁超时打断
- **可接受**: 这类场景通常意味着配置问题或数据异常,应该被中断并告警

### 3. Dify API 超时

**优化**: 20秒 → **30秒**

**理由**:
- 对标 `WRITE_OPERATION_TIMEOUT=30秒`
- 拉取大量会话/消息列表可能较慢
- 与重试机制配合(3次重试,指数退避)
- 平衡可靠性和响应速度

### 4. 代码改动

#### 新增常量 (`utils/constants.py`)

```python
# Consolidation operation timeouts (for batch memory consolidation)
CONSOLIDATION_TIME_BUDGET: int = 300  # 5 minutes
CONSOLIDATION_LOCK_TTL: int = 600  # 10 minutes
CONSOLIDATION_DIFY_TIMEOUT: float = 30.0  # 30 seconds per API call
```

#### 工具代码更新 (`tools/consolidate_long_term_memory.py`)

1. 导入新常量
2. 使用 `CONSOLIDATION_TIME_BUDGET` 替代硬编码的55秒
3. 使用 `CONSOLIDATION_LOCK_TTL` 替代硬编码的3600秒
4. 初始化 DifyClient 时传入 `CONSOLIDATION_DIFY_TIMEOUT`

#### DifyClient 更新 (`utils/dify_client.py`)

- 默认超时从20秒增加到30秒
- 添加文档说明超时参数的作用

## 影响评估

### 正向影响 ✅

1. **完整性提升**: 更多用户能在一次运行中完成记忆巩固
2. **减少 PARTIAL_SUCCESS**: 降低因时间预算不足导致的部分成功
3. **更快的故障恢复**: 锁TTL从1小时降至10分钟
4. **代码可维护性**: 超时参数集中管理,不再硬编码

### 潜在风险 ⚠️

1. **单次运行时间更长**: 5分钟 vs 55秒
   - **缓解**: 这是批处理任务,5分钟是可接受的
   
2. **锁超时风险**: 极端慢的场景可能被10分钟TTL打断
   - **缓解**: 
     - Checkpoint 机制保证中断后可恢复
     - 这类场景通常是异常,应该被打断
     
3. **Dify 工作流超时**: 如果工作流有整体超时限制
   - **缓解**: 
     - 建议使用异步工作流节点(如果Dify支持)
     - 或者调整工作流的超时设置为10分钟以上

### 向后兼容性

✅ **完全兼容**: 
- 不影响已有的 checkpoint 数据结构
- 不影响其他工具(add_memory/search_memory等)
- 锁机制向后兼容(只是TTL变化)

## 最佳实践建议

### 1. 监控指标

建议监控以下指标:
- 任务平均执行时间
- 超时率(超过5分钟的任务比例)
- 锁冲突率(获取锁失败的频率)
- PARTIAL_SUCCESS 比例

### 2. 告警阈值

- 单次任务执行 > 8分钟: 警告(接近TTL)
- 单次任务执行 > 10分钟: 严重(可能被锁超时打断)
- 锁冲突率 > 1%: 检查工作流配置(不应该有并发)

### 3. 调优建议

如果5分钟仍不够(监控显示频繁超时):

**选项A: 增加时间预算**
```python
CONSOLIDATION_TIME_BUDGET: int = 600  # 10 minutes
CONSOLIDATION_LOCK_TTL: int = 1200  # 20 minutes
```

**选项B: 减少每次处理的数据量**
- 降低 `conversations_limit` (默认20 → 10)
- 降低 `messages_limit` (默认20 → 10)
- 分批处理用户(每次处理更少用户)

**选项C: 分阶段处理**
- 第一阶段: 只扫描和写入 semantic 记忆
- 第二阶段: 补充 episodic 和 procedural

### 4. 生产环境配置

对于生产环境,建议:

```yaml
# Dify 工作流配置
consolidate_long_term_memory:
  schedule: "0 2 * * *"  # 每天凌晨2点(低峰期)
  timeout: 900  # 15分钟(工作流整体超时,大于 CONSOLIDATION_TIME_BUDGET)
  retry: 1  # 失败重试1次
  users_per_run: 10  # 每次处理10个用户
  conversations_limit: 20  # 每用户最多20个会话
  messages_limit: 20  # 每会话最多20条消息
```

## 总结

| 参数 | 原值 | 新值 | 提升 |
|------|------|------|------|
| Time Budget | 55s | 300s | **5.5倍** |
| Lock TTL | 3600s | 600s | **-83%** (更快恢复) |
| Dify Timeout | 20s | 30s | +50% |

**核心改进**:
- 🎯 **适配使用场景**: 从"实时工具"转向"批处理任务"
- 📈 **完整性优先**: 保证每日巩固任务能完整处理用户数据
- ⚡ **更快恢复**: 锁TTL大幅降低,减少故障影响
- 🔧 **可维护性**: 超时参数统一管理,便于调优

**预期效果**:
- PARTIAL_SUCCESS 率从 ~30% 降至 <5%
- 锁冲突恢复时间从1小时降至10分钟
- 支持每用户平均处理100-200条消息(vs 原来的~20条)
